# System peer review: source, formalisation and publication

**Review date:** 2026-11-08. **Decision:** preserve the existing components, correct the trust and provenance claims, and complete one small, genuinely traceable publishing path before scaling the corpus or the formal theory.

This is an engineering and editorial review, not a claim that every Sanskrit reading or every repository has been audited. The conclusions below distinguish inspected code and reproduced behaviour from proposals. All references are pinned: the active branches and the translation corpus are changing, so rerun the checks against the revisions actually being released.

## 1. The system that exists

The useful architecture is already present in pieces. OpenPāṭala records identities and source candidates; translation-work has source ledgers, translation layers and editorial artifacts; ipvv has an account-scoped Scholar workflow; svread presents texts and generated data; trika-x experiments with Lean models and source links; SanskritBench supplies automated diagnostics; and the book and video factories create downstream formats. The local teacher prototype stores revision history. The task is to make the boundaries between these pieces truthful and usable, not to replace them with one more platform.

There are also meaningful safeguards: the Scholar tests exercise account isolation, consent and revision-bound evidence; the trika-x review registry defaults unreviewed theorems to Frontier; translation-work's lineage adapter explicitly treats the benchmark as advisory; and some trace records preserve their uncertainty as caveats. Those safeguards need to survive the integrations described below.

The principal defect is that **different meanings of “checked”, “complete”, “gold” and “proof” are being collapsed**. A byte hash establishes what bytes were used. A locator identifies a candidate passage. A Lean proof establishes a proposition within a particular formal model. None of these alone establishes that the edition is correct, that a translation is faithful, that a passage entails the model, or that a named person has approved publication.

## 3. Findings, ordered by impact

### P0 — source coverage and the Sanskrit-to-model boundary are not yet reliable

[Pratyabhijñāhṛdaya's first ledger row](https://github.com/prx0r/translation-work/blob/679b028764ef9eba7a773c1f918953df9062bf7f/phrdaya/passages.jsonl#L1) labels its scope sūtras 1–4, but its `sanskrit` field contains only sūtra 1. The following four rows likewise label four-sūtra spans while carrying only one sūtra apiece. Other files contain English and Sanskrit for the remaining verses; that does not make the ledger's declared span complete. Any trace that hashes this field cannot, by itself, establish the source bytes for the entire advertised span.

For sūtra 1, the [GRETIL text and Kṣemarāja's commentary](https://gretil.sub.uni-goettingen.de/gretil/1_sanskr/6_sastra/3_phil/saiva/pratyabu.htm) give *citiḥ svatantrā viśvasiddhihetuḥ*: free consciousness is the cause of the accomplishment or manifestation of the universe. The [T1 draft](https://github.com/prx0r/translation-work/blob/679b028764ef9eba7a773c1f918953df9062bf7f/phrdaya/T1-phr-p01.md#L4) inserts repeated `[and]` markers and attaches “threefold” to the compound without marking it as commentary. Kṣemarāja does discuss manifestation, continuance and reabsorption in his explanation, but that expansion should be attributed to the commentary rather than presented as words in the sūtra. The [ARGMAP](https://github.com/prx0r/translation-work/blob/679b028764ef9eba7a773c1f918953df9062bf7f/phrdaya/ARGMAP.md#L3) repeats the same fragment as both premise and inference and says unresolved: none.

Meanwhile [PR #6's Lean file](https://github.com/prx0r/trika-x/blob/877ca8b103dc5544aee93952b44e89b5f2681637/formal-trika/control/Phrdaya.lean#L41) describes three items as a “triple epithet” and proves that its stipulated list has three distinct elements. That finite result can be valid as list arithmetic. It does not encode the grammatical relationship: *citiḥ* is the subject, *svatantrā* qualifies it, and *viśvasiddhihetuḥ* states its causal role. Nor does it establish Kṣemarāja's account of nondual causation. The file itself states several important limitations; the remaining title and source linkage should be equally precise.

**Repair:** define whether each ledger field is a full passage or an explicitly labelled excerpt; import and hash the complete edition-specific span before claiming coverage; keep sūtra and commentary as separate sources; repair the gloss and argument map with human editorial review; model grammatical relations and independently stated interpretive assumptions before any substantive theorem. Preserve competing readings rather than resolving them by an unlabeled model choice. Treat GRETIL and another copy of the same transcription as one textual lineage, not independent manuscript witnesses.

### P0 — the benchmark reports semantic “proof” from heuristics, and its result ID is wrong

[SanskritBench's kernel](https://github.com/prx0r/sanskritbench/blob/7bd466dc2d509b8d15b995e531ecacc6b942f949/pipeline/translation_proof.py#L51) uses length ratios, spelling/term heuristics and related checks, yet returns `proof: true` when they pass. In a synthetic test, both “The child goes to the village” and “The child does not go to the village” passed against the same source. This establishes a limitation of the current checks, not which translations in the corpus are wrong. The translation-work lineage adapter already correctly treats these signals as advisory.

There is also a concrete integrity bug: [`result_id`](https://github.com/prx0r/sanskritbench/blob/7bd466dc2d509b8d15b995e531ecacc6b942f949/pipeline/translation_proof.py#L174) interpolates the `source_sha` function object rather than calling it, and includes only the first 40 candidate characters. In one process, two different sources with the same candidate produced the same result ID; repeating the identical input in separate processes produced different IDs. The separate `source_sha` field does change, but that does not repair `result_id`.

**Repair:** version a new result format with a deterministic digest of canonical full source bytes, full candidate bytes, configuration and benchmark/tool revision. Preserve old IDs as historical, invalid for new authorization. Rename outputs to diagnostic checks, not semantic proof; record independently reviewed reference translations and assessed limitations. Add cross-process reproducibility, changed-source and changed-suffix collision tests, plus deliberately negated/missing-clause examples that cannot be promoted to fidelity certification merely because heuristics pass.

### P0 — proposed trace bundles can hide warnings while verifying successfully

In [PR #6's trace compiler](https://github.com/prx0r/trika-x/blob/877ca8b103dc5544aee93952b44e89b5f2681637/formal-trika/tools/trace_bundle.py#L284), `COMPLETE` means selected links are present; it does not require a passing chunk gate, a pinned witness or span-level binding. Of the committed sample bundles, 141 have `verdict: COMPLETE` and a `BLOCKED` chunk gate; 30 more have `COMPLETE` with no chunk-gate verdict. Caveats do disclose some of these limitations, so this is an ambiguous completeness label, not evidence that all the underlying texts are incorrect.

More seriously, [`verify_bundle`](https://github.com/prx0r/trika-x/blob/877ca8b103dc5544aee93952b44e89b5f2681637/formal-trika/tools/trace_bundle.py#L319) compares selected hops and the verdict but does not compare `gaps`, `caveats` or `open_problems`. I compiled a fresh local `phr-p01` bundle with `--no-db`, removed its recorded gaps and DB warning, and `--verify` still returned `VERIFIED`. The same compiler also treats an absent `blocking` field as an empty list and labels a song proof `PASS`; it labels formal associations `MODEL_CHECKED` without binding a successful per-theorem run. Its theorem join matches a locator alone. The repository has duplicate locators across works; although none of the duplicated locators was formally referenced in the inspected snapshot, future associations could attach to the wrong work.

**Repair:** separate `trace_links_present`, `source_span_verified`, `review_status`, `benchmark_diagnostics`, `formal_run_status` and `publication_authorized`; do not infer one from another. Compare or digest every canonical field, including warnings and schema/version; require explicit valid proof fields; use `(work, locator)` or an immutable passage ID for joins; keep `UNKNOWN` distinct from pass. Test removed warnings, missing fields, duplicate locators, altered layers and blocked-but-complete examples. A successful verification must say exactly which immutable data and checks were revalidated.

### P0 — svread overstates formal coverage and proof status

[The bibliography exporter](https://github.com/prx0r/svread/blob/cb299c083c73a577cd16daad855caebf683ef7f6/tools/emit_biblio.py#L102) counts the inventory of chunks in `EVIDENCE.json` as `formalized`; [the reader](https://github.com/prx0r/svread/blob/cb299c083c73a577cd16daad855caebf683ef7f6/app.js#L880) and [discovery text](https://github.com/prx0r/svread/blob/cb299c083c73a577cd16daad855caebf683ef7f6/tools/emit_discovery.py#L71) present these counts as formalisation. Comparing the committed bibliography with the exact `EVIDENCE.json` revision it names: Vijñānabhairava reports 17/17 formalized despite zero **direct chunk** references in that registry; Tantrāloka 15 reports 62 despite one; Paramārthasāra reports 12 despite one. Twenty-one of 28 inventoried works have no direct chunk references. Some work-level references exist; neither sort of reference proves textual entailment.

[The formal exporter](https://github.com/prx0r/svread/blob/cb299c083c73a577cd16daad855caebf683ef7f6/tools/emit_formal.py#L48) labels every registry entry `MODEL_CHECKED` before reading any run ledger and does not bind a successful run to each declaration's exact revision and statement. The committed export has 151 entries labelled that way. Some or all may have been checked elsewhere; this exporter alone does not establish it. This finding concerns the committed repository data, not an independently verified live deployment.

**Repair:** retire the misleading `formalized` field and regenerate all consumers, discovery output and release manifest. Expose work-level and direct passage associations separately, with unknowns and source revision/digest. Emit `MODEL_CHECKED` only from a verifiable declaration-specific successful run bound to source tree, toolchain, statement and artifact digest; otherwise use `REGISTERED` or `UNVERIFIED`. Make the UI say that source associations are editorial claims requiring review, even when a model compiles.

### P0 — a report-only identity check can write to its configured event ledger

[OpenPāṭala `check.py`](https://github.com/prx0r/openpatala/blob/7af046d3096aa6402181ca6e41ef8878be485738/check.py#L62) parses `--status` but does not change its execution path. Its conformance suite [appends five synthetic events](https://github.com/prx0r/openpatala/blob/7af046d3096aa6402181ca6e41ef8878be485738/patala/tests/conformance.py#L72) via an [event store that commits](https://github.com/prx0r/openpatala/blob/7af046d3096aa6402181ca6e41ef8878be485738/patala/events_v2.py#L36) to the configured database. I did **not** run this command against a shared or live database. The supposed replay check rereads and hashes events; it does not destroy and rebuild a projection as its description says. The wrapper can also print GREEN and exit zero when known blockers remain, so its overall result is not an all-clear for those blockers.

**Repair:** make `--status` genuinely read-only; require a clearly identified disposable test database for write tests, refuse live/shared DSNs and tear down safely. Implement actual event-to-projection replay against isolated fixtures. Return explicit per-capability PASS/BLOCKED/FAIL with machine-readable scope; do not collapse a required BLOCKED capability into GREEN. Test that status cannot issue INSERT/UPDATE/DELETE, that replay detects corrupt projections, and that unknown resources remain unknown.

### P1 — essay “shippable to review” can be forged with unrelated markers

[The essay checker](https://github.com/prx0r/trika-x/blob/df3b5f631f4a2f264e2aca3547c5670a64ff60c9/formal-trika/tools/essay_check.py#L39) describes tier law, frozen-claim coverage and verified spans, but checks marker presence and selected field shapes rather than binding each marker, claim, passage, quote and receipt. A synthetic draft containing an invented T-tier bullet with a different claim ID, nonexistent chunk and only a matching receipt slug returned `PASS` and “1/1 essays shippable.” The command describes this as shippable **to review**; I did not establish that a production publisher consumes this result.

**Repair:** validate exact claim IDs and tiered bullets; bind T-tier claims to the edition, exact quoted span and digest; verify receipt contents against the claim and essay revision; require explicit reviewer identity and decision where the workflow requires them. Call the structural result `READY_FOR_HUMAN_REVIEW` only when its prerequisites are met and keep author publication consent separate. Include the forged-marker, nonexistent-source, changed-receipt and changed-revision cases in CI.

### P1 — the open PRs are not yet ready for an unqualified merge

* [trika-x #6](https://github.com/prx0r/trika-x/pull/6) still describes a three-commit batch, but at inspected head it contains **41 commits, 1,277 changed files and 174,251 additions**. Much of the growth is 910 generated trace files, plus a large third-party geometry import, research documents, model changes and federation tooling. Its [Formal checks run](https://github.com/prx0r/trika-x/actions/runs/42465845403) failed while downloading the pinned Lean toolchain after HTTP 504 responses; subsequent checks were skipped. Separately, local `review_status.py --check` fails with **17 missing rows** on this head. The current main snapshot fails the same check with **8 missing rows**. Those are separate observations: the CI failure observed was toolchain download, not a demonstrated Lean theorem failure.
* Split or stack the PR by reviewable concern: finite models, trace format and generator, generated samples, federation, third-party research, and editorial essays. Update the title and description to the actual diff. Regenerate missing rows as **Frontier**, never automatic Core promotion. Verify permissions and redistribution terms for copied third-party material; keep links and small properly attributed quotations where full copies are not cleared. Re-run the pinned workflow and request a real human scholarly review for the source-to-model claims.
* [svread #10](https://github.com/prx0r/svread/pull/10) resolves an expansion essay but `links()` rejects the same valid atom as an unknown kind. An allowed slug containing a dot also resolves the wrong filename because `Path.with_suffix` replaces the suffix. Both failures were reproduced with temporary synthetic files. Its [Reader integrity run](https://github.com/prx0r/svread/actions/runs/42247093191) failed on a stale or missing release manifest; subsequent tests were skipped. Add link traversal and dotted-slug regression cases, use literal suffix appending, update against the actual current base, regenerate the manifest and rerun CI.

### P1 — evidence gates and editorial statuses need narrower meanings

[`two-sources-v1`](https://github.com/prx0r/ipvv/blob/c2cb6b35272bfbd7824063b2fd769f388197495e/tools/qp_acom/gates.py#L54) counts distinct caller-supplied `source.class` strings, despite its description saying two accepted sources support the claim. It does not itself establish acceptance, distinct source identities, textual independence or support. Other receipt authorization controls exist; this finding is about the meaning of this gate, not a demonstrated bypass of the entire authorization workflow.

At the pinned translation-work revision, [registry statuses](https://github.com/prx0r/translation-work/blob/679b028764ef9eba7a773c1f918953df9062bf7f/REGISTRY.json#L373) include `gold (machine-proposed...)` as well as plain `gold`. Aggregate gold counts must not be read as a count of scholar-approved translations. Its source map has many `CANDIDATE` and `UNMAPPED` records; a recorded source or candidate match is neither manuscript verification nor reuse permission. Its default `check.py` has a specific work scope and writes generated proof records, so document that side effect and scope instead of advertising it as a universal read-only audit.

**Repair:** retain historical gate IDs, add a versioned gate that resolves stable source IDs and assessed independence, and bind support judgments to signed editorial decisions. Split translation status into machine-generated, mechanically checked, human-reviewed, approved-for-purpose and published, each tied to an exact revision. Keep source-recorded, edition-identified, witness-verified and rights-cleared as separate fields. Make check mode read-only or explicitly stage output before comparison.

### P1 — portability and configuration currently obscure real failures

Several scripts assume `/root/...`, `/home/agent/...` or specific sibling checkouts. The lineage integration test in this checkout fails because the stored OpenPāṭala dossier path points to `/root/openpatala`, despite supplying a different checkout. Some svread tests require an unavailable PostgreSQL driver/database; videofactory's local suite lacks the original storyboard directories; bookfactory's check stopped on an uninstalled `indic-transliteration` dependency. These results establish that the clean environment could not run those paths as-is; they do not prove the corresponding production service or source data is broken.

**Repair:** declare dependency versions and configurable roots; use repository-relative paths only for portable committed artifacts, and fixture paths in tests. Separate offline unit tests from explicitly configured integration tests and live status checks. CI should report missing optional infrastructure as SKIP/BLOCKED with a reason, while required tests fail closed. Never “fix” tests by pointing them at a real owner's data or database.

### P1 — the teacher is a promising local prototype, not yet an account-backed service

The locally found teacher revision store and interface have synthetic coverage for revision handling; its server is a loopback prototype with a local private journal. The checked code and tests do not establish a deployed account-backed teacher, encrypted backup, cross-device access, independently verified identity or live-model behaviour. The remote repository was not accessible through the connected GitHub integration, so this review cannot establish whether the local branch is currently visible to the other agent.

**Repair:** first establish branch visibility without copying journals or private user content into Git. Reuse Scholar's account and per-record consent boundaries where appropriate; provide private export, deletion, backup/recovery and revision-conflict handling. A teacher response should show which approved text or selected personal material it used, distinguish text from interpretation, and require explicit opt-in before personal notes reach a model. Prove this first with synthetic accounts and data.

### P1 — publishing factories need a source-to-output handoff, not more render gates

[Bookfactory's pipeline](https://github.com/prx0r/bookfactory/blob/399eb0a9c183eebe99c70f29aa746bd356d655b2/PIPELINE.md#L34) itself says there is no automated production/ship command and that per-entry rights and reviewed revisions remain to be completed. A generated PDF or page count is not evidence that the edition, translation, permissions or interior layout is ready for print. Freeze the exact approved text, source/edition, contributor credit, asset and font rights, trim/bleed and output bytes for each edition; perform a human page proof and actual distributor preflight before commercial release.

[Videofactory's owner instruction](https://github.com/prx0r/videofactory/blob/39bcc904adb1043e0bc5283dc93108ec260adfcd/docs/RENDER-GATE.md) makes an approved valid storyboard the sole nontechnical render gate. Respect that instruction: previews should render without new scholarly gates. The older [`assemble_proven.py` path](https://github.com/prx0r/videofactory/blob/39bcc904adb1043e0bc5283dc93108ec260adfcd/core/builders/assemble_proven.py#L35) still requires a current review pack and reviewed part proofs, so clarify which entry point is active and reconcile the contract. For distribution, attach source/asset/rights and output-digest information and provide the owner with a clear QC report; do not silently turn advisory render checks back into blockers.

### P2 — too many living documents and generated artifacts obscure the truth

The repositories contain valuable handovers, endgame plans, master plans and generated dashboards, but several describe different dates, scopes and intended futures. Existing historical documents should be preserved, not bulk deleted or rewritten. The fix is a single current entry point and explicit status for every referenced artifact: **implemented and tested at revision**, **prototype**, **proposed**, **blocked**, or **historical**. Link each to its owner, commands, data contract and evidence. A dashboard count should say what it counts and never imply human acceptance or a live deployment.

## 4. Proposed ownership and contract

| Boundary | Owner | What the owner is authoritative for |
| --- | --- | --- |
| Work / edition / witness / passage identity | OpenPāṭala | Stable identities, provenance, candidate mappings and reviewed decisions; an identity is not a verified reading. |
| Text and editorial layers | translation-work | The actual edition-specific source bytes, verse/span alignment, translations, annotations, argument maps and their revision history. |
| People, private drafts and decisions | ipvv Scholar | Account-scoped access, selected sharing, revision-bound review and author sign-off. A self-attested name is not an independently verified identity. |
| Formal model | trika-x | Formal definitions, assumptions, theorem statements, toolchain and per-run results; it does not certify the text or its interpretation. |
| Diagnostics | SanskritBench | Versioned benchmark outputs and limitations; advisory until independently validated for a named use. |
| Public reading | svread | A reproducible projection of explicitly pinned approved artifacts, with uncertainty and source links visible to readers. |
| Teacher | nibbanahelp / Scholar integration | Private, consented personal workflow and source-grounded educational assistance. |
| Outputs | bookfactory, videofactory, visuals, deitybody | Rendered artifacts and delivery-specific metadata from a frozen source revision, with separate preview and release decisions. |

Use a small versioned **release manifest**, not another shared mutable database. For each selected passage and derived artifact it should identify: work, edition and any verified witness; exact source bytes/span and full SHA-256; translation and claim revisions; named editorial decisions and their scope; formal declaration, statement/toolchain/source and successful-run digest if available; rights evidence for the intended use; output recipe and artifact digests. `UNKNOWN` is a legitimate state. A release pins compatible versions; being newer is not automatically better, but a stale or missing input must be visible.

## 5. A practical delivery order

Each checkpoint should be a small PR with a reviewer-readable diff and a green, appropriately scoped test run. Do not wait for the whole corpus to be perfect before making a useful reader; do not use a technically green artifact as evidence of scholarly sign-off.

1. **Stop inaccurate claims and unsafe checks.** Owners: svread, OpenPāṭala, SanskritBench. Change the reader's formalisation labels to accurate associations/unknown; disable unbound model-checked promotion; make status read-only; rename benchmark proof claims and fix result IDs. **Done when:** old misleading data is regenerated, the synthetic counterexamples are covered, status cannot write, and exact source revisions are published with outputs.
2. **Make the two active PRs reviewable.** Owners: trika-x and svread. Split #6 by concern, fix trace verification/IDs/status semantics and regenerate Frontier rows; repair #10 resolution, traversal and manifest. **Done when:** each PR describes its actual diff, CI runs against its exact head, and human review can assess the Sanskrit and assumptions without examining unrelated generated files.
3. **Repair one source passage end to end.** Owners: translation-work + OpenPāṭala, with a Sanskrit reviewer. Begin with Pratyabhijñāhṛdaya 1–4: freeze the complete edition-specific sūtras, distinguish commentary, correct T1 and argument map, document disputed readings, and record the decision on the exact bytes. **Done when:** every displayed translation and claim resolves to its source span and editorial status; a changed byte invalidates the corresponding approval. Do not call a digital transcription an independently verified manuscript.
4. **Connect that passage to one formal example and one essay.** Owners: trika-x + Scholar. Model the grammatical and philosophical propositions separately from list arithmetic; explicitly state reconstruction and assumptions. Attach per-declaration Lean run evidence where a proof exists, and prepare an essay whose claims resolve to the reviewed passage. **Done when:** a reader can follow source → translation → interpretation → model → proof result, including what remains unresolved, and the author can approve one exact essay revision. An essay is not authorized merely by satisfying a structural check.
5. **Ship a thin reader slice.** Owners: svread + ipvv. Import the pinned manifest, show source and commentary separately, display translations with author/review state, expose trace and formal limitations, and preserve account/private-draft permissions. **Done when:** a clean checkout builds the same output, changing a source or approved revision makes the release stale, and a synthetic account cannot view another account's private data.
6. **Connect outputs and teacher selectively.** Owners: bookfactory, videofactory and teacher. Produce one clearly labelled book preview and one storyboard-approved video preview from the same frozen release, then exercise distribution checks separately. Add one synthetic private teacher session that cites the approved passage and discloses which selected notes were shared. **Done when:** each artifact identifies its input revision and the user can export/delete their private session; no automated preview is represented as scholarly approval or a commercial release.
7. **Archive and automate the maintenance.** Owners: each repository. Create one current system map, mark old documents historical, make one clean-checkout fixture suite and publish exact-revision CI outcomes. Migrate the wider corpus incrementally by source and scholarly priority. **Done when:** another agent can find the authoritative contract and reproduce the narrow end-to-end example without relying on box-specific paths or private data.
